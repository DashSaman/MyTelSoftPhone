# Android v3 verification evidence

Scope: retained Linphone SDK, Android package `one.mytel.softphone`, version `3.0.0` / `30000`. Test environment: existing Android 15/API 35 x86_64 emulator with ARM translation, Issabel/Asterisk at the authorized LAN PBX, isolated extension 301. Extensions 1/2 were not used by these Android checks.

## Regression evidence

- `628099c`: connection-status tests initially failed compilation because the new status policy did not exist. `f574910` implements it and moves all chip SDK access/listener management to the core thread; the four policy cases pass.
- Number normalization has 19 passing cases. A retrospective comparison of the original `02da50d` normalizer against the expanded suite ran 19 tests with four failures: Persian feature codes, nonnumeric Iranian prefixes, `tel:` input, and pasted directional/spacing characters. Current normalizer ran 19/19 passing. This comparison was performed after implementation; it is not claimed as an earlier runtime RED run.
- The preexisting managed-configuration tests exposed two actual provisioning-URI precedence failures. The URI is now compared after inline XML is applied. The empty-restrictions fixture was corrected to explicitly represent previously applied MDM; an added test preserves personal accounts when MDM has never been configured. All 17 tests pass.
- Login attempt coordination and removed-account alert coverage are recorded separately in `login-security.tdd.md` and `registration-alerts.tdd.md`.
- At final source `f4e46de`, the freshly executed local unit suite passed 75 tests, zero failures/errors/skips: managed configuration 17, connection status 4, directory parser 16, number normalizer 19, login attempt coordinator 5, registration-alert policy 6, account-error notification policy 8. Command: `gradlew.bat :app:lintDebug :app:testDebugUnitTest :app:assembleRelease --max-workers=1 -Pkotlin.compiler.execution.strategy=in-process --console=plain` completed successfully in 10m 7s, including signed release packaging.
- Inspecting the actual lint XML, rather than only its SARIF severity, exposed 955 errors despite an inherited successful exit: 925 missing translations, 23 invalid plural overrides in unsupported locales, and seven thread constraints. `e70fe24`/`8f9bbf4` correct the SDK/UI thread paths and enable `abortOnError=true`. Packaging now matches the existing English-only UI locale declaration; Unicode messages and contact names are unaffected. `fa30f18` removes the 23 invalid plural overrides in unshipped Czech, Polish and Slovak resources, retaining the default English resources. No lint baseline or blanket suppression was added. The final enforcing run completed with **zero XML errors and 123 warnings**; remaining warnings are mostly inherited style/resource/deprecation suggestions, not a claim of warning-free code.
- Coverage percentage was not measured. These checks are not evidence that the complete inherited application is defect-free.

Final signed artifact at source `f4e46dee0d0519909dc74bcb76430fca8fcc6015`: `app/build/outputs/apk/release/MytellPhone-release-v3.0.0.apk`, 95,757,504 bytes, SHA-256 `a4ac640c1c62b10d998edf75f65cf7ac31f467d36a5863369795af84b17bcfb9`. `apksigner verify --verbose --print-certs` exited successfully and verified the v2 signature with the existing production certificate. Minimum Android API is 28, target API is 37. [Clean strict GitHub CI for this source](https://github.com/DashSaman/MyTelSoftPhone/actions/runs/43621419867) also passed.

## Follow-up runtime checks on the signed `fa30f18` build

- The cancelled-login regression returned to editable form, then to the original 301 account Online with no stale in-app banner.
- The corrected DTMF keypad was inspected during an actual PBX `*43` call in portrait and landscape. All 12 keys were visible above the gesture inset; landscape used the existing six-column layout with compact keys. Pressing `#` ended the call and the app displayed the remote-ended state.
- Created the isolated local contact `MyTelV3Lab Contact` with test extension 3099, edited the surname, added it to favourites, then deleted it through explicit confirmation. The contacts list returned to its original empty state.
- Light and dark settings and existing Persian/emoji chat were readable. The original Auto theme setting was restored. The inherited attachment picker explicitly displayed `Files are shared through files.linphone.org`; no attachment or recording was uploaded.
- With the app backgrounded on the launcher, a controlled 3099 audio call appeared in the native notification. Answer launched the connected call activity. The test microphone was muted; the actual Record/Stop recording controls created a 103,373-byte Matroska file with Opus mono audio at 48 kHz and a 25.081-second container duration. FFmpeg decoded 25.02 seconds; mean/max signal levels were -19.4/-15.1 dB and an independent frequency scan measured 440.0 Hz, matching the lab peer's generated tone. This verifies receive/decode/record media, not subjective microphone/speaker quality.
- A native-notification defect was reproduced independently: a newly created dummy 87651 account at reserved documentation IP `192.0.2.1` was cancelled and removed; around 30-40 seconds later its delayed SDK failure created a fresh registration-error notification despite 301 remaining Online. `767d44a` adds eight failing policy tests and `f4e46de` implements notification membership/removal/startup cleanup; all eight pass both standalone and within the final 75-test Gradle run.
- After a real guest Android reboot, the SDK reconnected 301 Online and retained the complete 302 Persian/emoji conversation and the outgoing-only 3099 test message. The app was stopped, its private test data backed up, and the emulator closed to free build memory. This guest-reboot check avoids relying on a stale emulator QuickBoot snapshot; future emulator host launches explicitly disable snapshot loading.

## Final `f4e46de` device regression

- Cold emulator boot with snapshot loading disabled retained the tested conversations and 301 Online without a data restore.
- A synthetic orphan notice for 87653 was first reproduced on the preceding build. It disappeared during the package upgrade. No matching application-side cancellation log was observed, so that disappearance is not claimed as runtime proof of the startup-cleanup branch; that branch has unit/source verification.
- `adb install -r` of the final APK succeeded with the same signing identity and retained the original 301 account and conversations.
- Primary dummy 87652 and separate third-party SIP dummy 87654 at `192.0.2.1` both showed pending Cancel controls and returned to editable forms. More than 45 seconds after the second cancellation, 301 remained Online, no stale in-app banner appeared, and the Android notification list contained zero `Account Error` notices. Screenshots: `android-v3-fixed-cancel-after-45s.png`, `android-v3-fixed-no-orphan-notification.png`.
- Dialer correction was checked in the final APK: long-press Delete cleared the draft; with the input field focused, a caret inside `312` allowed keypad Delete to produce `32`, then inserting `0` at the caret produced the reviewed target `302`. No call was placed to the temporary test drafts.
- Real Windows 302 to Android 301 video was answered through the native Video action on the final APK. After explicitly enabling the Android synthetic camera, both applications displayed the other side's image without a crash. In the controlled common-VP8 run, Windows reported transmit 327 kbit/s at 640x480/14.84 fps and receive 119 kbit/s at 480x640/11.54 fps, with 0% packet loss in that snapshot. Android logged sustained VP8 decoding around 15 fps. Both microphones were muted for privacy; camera images remain private and are not published.
- Blind transfer completed across the real applications: Windows 302 transferred its active controlled 3099 call to Android 301. Android received caller 3099 in the native notification, accepted Audio Answer, and remained connected while the Windows call window closed. The PBX showed 3099 bridged to 301 Up; Android explicitly ended the transferred call after observation.
- The final reverse video call was started from Android's reviewed `302` dialer target with the explicit Video call action. The final Windows incoming call window appeared and was manually answered; after Windows enabled its video, Android displayed the real Windows camera frame and Windows displayed the animated emulator image. The PBX captured both sides SendRecv VP8 with ulaw audio and zero packet loss in the observed snapshot. Android explicitly ended the connected call and returned to main Calls Online.
- The initial receive-only mode behind this emulator's `10.0.2.16` NAT remained black until Android enabled its camera and transmitted media. This also occurred with a single common video codec, so codec preference alone is not established as the cause; the observed behavior is consistent with an unopened RTP NAT mapping. Receive-only video through this emulator NAT is not claimed as passing, and that NAT explanation remains an inference. PBX codec alignment and appropriate media/NAT traversal configuration (for example STUN/ICE/TURN or an SBC relay, as applicable) remain deployment requirements. The first mixed-codec call and the second common-VP8 call were distinguished; only the latter established actual pictures in both directions.
- The first reverse-video attempt rang for 30 seconds and timed out before Windows answered. Both attempt records were present in the SDK database and in the SDK's 22-item history result, with ordinary non-conference metadata. The list had retained its older viewport anchor; clearing the temporary search/scrolling to the top revealed the new 21:56 rows. This was not storage loss, timezone loss or proof of conference misclassification. No history record was deleted or suppressed to hide SDK fallback attempts.
- After the final media checks, the original 301 identity remained registered, the Auto theme and original rotation settings were restored, the synthetic contact had been removed, and a fresh private test-data backup was saved before closing the emulator. Call/chat test records were retained as evidence; credentials and camera images were not published.

## Follow-up fixes and remaining acceptance checks

- Cancellation exposed a stale global account-error banner despite the surviving account being Online; `f4f93a6` fixes the policy, and the final banner regression passed as recorded above. The separately reproduced native-notification defect is fixed in `f4e46de` and passed the delayed-callback device regression above.

- New installs now have no public attachment service default. Existing custom/inherited profiles remain intact. The attachment picker displays its destination host, without URL credentials/query/path. Settings explains that attachments need a separate file service. No files or voice recordings were uploaded to a public service during testing.
- A compound visibility expression in that new caption caused a clean CI DataBinding code-generation failure. `0034614` simplifies it. Exact-source kapt, Kotlin and Java compilation passed locally, and the clean strict GitHub CI at `fa30f18` passed. The caption was subsequently verified in the running signed APK.
- No physical Android handset was connected. Subjective microphone/speaker quality, vendor battery restrictions, long background/reboot reliability, external PSTN carrier calls, configured attachment delivery and a full device matrix are not established by emulator/unit tests.
- Native lab helpers also failed independently during media setup. Their failures are not labelled as application failures or passing video tests.
- Two SDK history records (zero-duration Aborted followed by success) were observed for an outgoing call, including in records predating v3. PBX showed one real call. Root/research investigation distinguishes this SDK fallback artifact from a proven app double-dial.
